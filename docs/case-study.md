## 1. 왜 시작했나

AI Agent를 이용한 개발에 대한 접근중에서 지시만 하고 그 결과에 대해서 내가 확인 한것을 알 수 없는 것에 대해서 다른 방법으로 접근을 해보고 싶었다. 

그래서 **실제로 돌아가는 서비스 하나를 끝까지 만들면서, AI와 일하는 방식을 함께 정리하기로 했다.** 주제는 공개 API로 구할 수 있는 한국 경제 지표로 정했다. 데이터가 공식적이고, 수집·저장·조회·배포를 모두 거쳐야 해서 방식을 시험하기에 알맞았다.

## 2. 목표와 범위

- **목표:** 한국은행 ECOS, 통계청 KOSIS, 공공데이터포털의 공식 통계를 하루 한 번 모아 한 화면에 보여 준다.
- **MVP는 조회만 한다** ([D017](../records/07.decision/decisions/KEDP001-D017.md)): 수집 → 저장 → 조회. 지표 비교, AI 분석, 검색, 예측은 2차로 미뤘다.
- **하지 않기로 한 것:** 유료 데이터, 비공식 API, 웹 스크래핑([D001](../records/07.decision/decisions/KEDP001-D001.md)), 회원과 다운로드([D003](../records/07.decision/decisions/KEDP001-D003.md)), 장애 대비 설계([D020](../records/07.decision/decisions/KEDP001-D020.md))
- **기술:** TypeScript(React) 화면, Go 수집·API, Rust 응답 처리(gRPC), PostgreSQL, Docker([D002](../records/07.decision/decisions/KEDP001-D002.md))

- **규칙은 파일로 남긴다** ([D009](../records/07.decision/decisions/KEDP001-D009.md)): [.claude/CLAUDE.md](../.claude/CLAUDE.md)에 문서 위치, 역할, git 규칙을 둔다. 대화가 바뀌어도 Agent가 같은 규칙으로 시작한다.
- **결정은 기록으로 남긴다:** 결정 문서 24개([records/07.decision/decisions/](../records/07.decision/decisions/)). Agent가 `proposed`로 쓰고 소유자가 `decided`로 바꾼다. 이미 결정한 것은 다시 묻지 않는다.
- **Issue는 다섯 칸으로 쓴다** ([D014](../records/07.decision/decisions/KEDP001-D014.md)): 할 일, 고쳐도 되는 곳, 정해진 것(다시 묻지 않는다), 끝났다는 기준, 하지 말 것. 예: [#48 방문자 수](https://github.com/schware/aidev-KEDP001/issues/48)
- **비밀은 Agent에게도 보이지 않는다** ([D012](../records/07.decision/decisions/KEDP001-D012.md)): 키와 비밀번호는 서버의 `.env`에만 둔다. 대화, 문서, 저장소에는 쓰지 않는다.

## 5. 어려웠던 점과 해결

### 5.1 API를 보기 전에 DB를 설계하지 않았다

- **문제:** 제공처 세 곳의 응답 모양이 모두 다르다. 문서만 보고 DB를 짜면 실제 응답과 어긋난다.
- **해결:** DB 설계를 일부러 미뤘다([D004](../records/07.decision/decisions/KEDP001-D004.md)). 먼저 요청 값을 넣으면 응답을 파일로 저장하는 샘플 도구를 만들었다(#22). 실제 응답을 [samples/](../samples/)에 모은 뒤 저장 방식을 정했다([D022](../records/07.decision/decisions/KEDP001-D022.md)).
- **결과:** 실제 응답에서만 보이는 차이를 처음부터 설계에 넣었다. 예를 들어 KOSIS는 연 주기를 `Y`로 요청하면 응답에서는 `A`로 온다. 단위 칸이 없는 표도 있다([10.indicators](../specification/10.indicators/README.md)). Agent에게는 "확인하지 않은 지표 코드를 사실처럼 쓰지 않는다"를 규칙으로 두었다.

### 5.2 개발 서버가 멈췄다

- **문제:** 메모리가 작은 개발 서버에서 Claude Code 2개와 Docker 작업 3개를 함께 돌리자 서버가 멈췄다.
- **해결:** 원인을 "동시에 돌리는 것"으로 좁혔다. image는 하나씩 만들고(`deploy/build.sh`), Rust compile은 2개씩만 돌게 했다. 서비스는 별도 실행 서버로 옮겼다([D023](../records/07.decision/decisions/KEDP001-D023.md)).
- **결과:** 개발 서버는 만드는 곳, 실행 서버는 돌리는 곳으로 나눴다. 실행 서버에는 소스 없이 image, compose, `.env`만 둔다.

### 5.3 container로 나누자 관리자 허용 IP 검사가 틀어질 뻔했다

- **문제:** Go는 같은 서버(`127.0.0.1`)의 proxy만 믿고 접속 주소를 읽었다. nginx와 Go를 container로 나누면 nginx의 주소가 Docker 내부 주소가 된다. 그러면 관리자 허용 IP 검사가 맞지 않는다.
- **해결:** 배포 방식을 결정하는 단계에서 이 영향을 먼저 적었다([D023](../records/07.decision/decisions/KEDP001-D023.md) "영향"). 믿을 proxy 대역을 설정으로 받고, nginx가 실제 접속 주소를 넘기게 했다(#46).
- **결과:** 실행 서버로 옮긴 날 관리자 화면이 허용 IP에서만 열리는 것을 확인했다.

### 5.4 200개 지표 설계서를 그대로 받지 않았다

- **문제:** MVP 뒤에 대한민국 거시경제 지표 설계서(약 200개 KEY)를 바탕으로 지표를 늘리려 했다. 그런데 KEY 형식, 차원, 내부 계산 지표, 새 제공처가 지금 구조와 맞지 않았다.
- **해결:** 설계서를 지금 DB·API·화면과 하나씩 비교했다. 범위를 "핵심 세트 중 ECOS·KOSIS로 받을 수 있는 것, 증감률은 공식값만"으로 줄였다. 지표 id 규칙은 바꾸지 않았다. 지표가 늘어도 찾기 쉽게 구분 9개를 붙였다([D024](../records/07.decision/decisions/KEDP001-D024.md)).
- **결과:** 지표가 7개에서 42개로 늘었다. 지표 id와 화면 주소는 하나도 바뀌지 않았다.

### 5.5 KOSIS 표마다 다른 모양

지표를 늘리면서 KOSIS의 예외가 하나씩 나왔다. 그때마다 작은 Issue로 나눠 해결했다.

- 통계청이 아닌 기관(고용노동부, 관세청, 국토교통부)의 표는 기관 코드가 달라 받을 수 없었다 → 샘플 도구에 기관 코드 지정을 추가했다(#58).
- 같은 표에서 지표를 여러 개 받자, 시험 서버가 다른 항목의 응답을 돌려줬다 → 항목·분류 코드까지 맞춰 고르게 했다(#59).
- 분류가 둘째 자리에 있는 표는 응답에 첫째 자리 칸이 없어 오류가 났다 → Rust가 `ALL` 자리는 대조를 건너뛰게 했다(#60).

### 5.6 방문자 수를 세되 개인정보는 남기지 않았다

- **문제:** 하루 방문자 수를 세려면 같은 사람을 구별해야 한다. 그런데 IP를 저장하고 싶지 않았다.
- **해결:** 접속 주소, 브라우저 정보, 그날의 무작위 값으로 hash를 만들어 메모리에서만 비교한다. 날이 바뀌면 버린다. DB에는 날짜별 숫자만 둔다(#48).
- **결과:** 서버를 다시 켜면 같은 사람을 한 번 더 셀 수 있다. 이 오차는 받아들이기로 Issue에 적었다.

## 6. 결과

- 지표 42개, 구분 9개, 제공처 3곳을 하루 한 번 자동으로 수집한다.
- 실행 서버에서 Docker container 4개(nginx, Go, Rust, PostgreSQL)로 운영 중이다.
- 사용자 화면(구분별 카드, 상세 차트)과 관리자 화면(지표 설정, 수집 시각, 제공처 상태, 방문자 수)이 있다.
- 결정 24개와 Issue 32개에 "왜 그렇게 했는지"가 남아 있다. 처음 보는 사람도 기록만 보고 따라갈 수 있다.
- 키가 저장소에 들어간 적이 없다. commit 전 hook과 PR 검사가 매번 확인한다.

## 7. 배운 것과 다음에 다르게 할 것

- AI Agent는 Github 를 이용해서 Issue 등록 방식으로 서로의 진행 사항을 관리 하면 큰 어려움 없이 개발이 진행된다.
- Go, Rust , TypeScript 를 배웠다고 할 수 없다. 내가 이번에 배운 것은 Github Issue 와 Claude Code 과 일하는 방법 이다.
- Source 에 대한 분석이나 속도적인 접근은 전혀 하지 못했다. 핑계라면 퇴근 이후에 주말에 해서 라고 할 수도 있지만 솔직하게 생각만큼 쉽지 않다.
- 지시하는 것만으로 어렵다. 내가 제대로 시켜야 하는 것이 가장 힘들다.

### AI Agent와 일하며 배운 것

- 내가 기준을 잡고 Issue를 수립 해야 한다.
- 내가 만들고 싶은 것에 대해서 알아야 한다.

### 힘들었던 점

- 이 작업은 그렇게 힘든 것이 없었다.
- API 연동 일뿐이고 크게 어려움이 있는 것은 아니였다.
- 어떤 데이터를 가져와서 어떤 데이터를 보여줄지에 대해서 Claude Code와 Copilot의 접근 방법이 달라서 Copilot 에서 더 찾아 보라고 시켜서 Claude Code에 추가 한 것 정도 있는 것 같다. 

### 다음 프로젝트에서 다르게 할 것

- Issue는 Issue 로 진행하고 개발 문서를 함께 확정 하는 방식으로 진행 하면 좋을 것 같다.

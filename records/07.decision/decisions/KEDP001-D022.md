# DB 저장 방식과 데이터 저장 규칙

## 결론

`specification/30.database/README.md`(DB 설계서 초안)의 추천안을 확정한다. 번호는 설계서의 번호와 같다(1~14는 6장 질문, 15~22는 "확인 못 함" 표).

### 1. 저장 방식과 DB에 쓰는 쪽

| # | 정할 것 | 결정 |
| --- | --- | --- |
| 1 | 저장 방식 | 혼합. 지표 정의 테이블 하나에 제공처별 코드(통계 코드, 항목 코드, 분류)를 함께 두고, 관측값 테이블 하나에 세 제공처를 모두 담는다. 원본 응답은 따로 둔다 |
| 7 | DB에 쓰는 쪽 | 관측값과 원본 응답은 Rust가 쓴다. 수집 기록, 지표 정의, 화면 설정, 수집 시각은 Go가 쓴다 |
| 14 | DB 접속 계정 | Go와 Rust를 나눈다. Rust는 관측값·원본 응답, Go는 설정·수집 기록을 다룬다. 비밀번호는 저장소에 쓰지 않는다 |

### 2. 값과 기간

| # | 정할 것 | 결정 |
| --- | --- | --- |
| 2 | 기간 저장 | 기간 시작일(date)과 응답 원문(예: `202401`)을 함께 저장한다 |
| 3 | 연 주기 코드 | `A`. 화면 명세와 KOSIS 응답이 `A`다. KOSIS 요청 값 `Y`는 요청할 때만 쓴다 |
| 8 | 공공데이터포털 값 | 종가(`clpr`)만 지표 값으로 쓴다. 나머지 값은 원본 응답에 남는다 |
| 9 | 화면 단위 | 응답 단위와 관리자가 넣은 단위를 둘 다 저장하고, 관리자 값을 우선한다 |
| 10 | 값 저장 형식 | 숫자(numeric)와 응답 원문 문자열을 함께 저장한다 |
| 15 | 빈 값(결측) | 관측값으로 저장하지 않는다. 원본 응답에는 남는다 |

### 3. 값이 바뀌거나 쌓일 때

| # | 정할 것 | 결정 |
| --- | --- | --- |
| 4 | 값이 고쳐졌을 때 | 새 값으로 덮어쓰고, 이전 값은 이력 테이블에 남긴다. 값이 실제로 달라졌을 때만 남긴다 |
| 11 | 관리자가 주기를 바꿨을 때 | 이전 주기 값은 남긴다. 관측값에 주기를 함께 저장한다 |
| 12 | 처음 수집할 과거 범위 | 지표의 차트 기간만큼 |

### 4. 원본 응답과 수집 기록

| # | 정할 것 | 결정 |
| --- | --- | --- |
| 5 | 원본 응답 | DB에 보관한다. 요청 주소는 키 자리를 `***`로 가린 형태로만 저장한다 |
| 6 | 원본 보관 기간 | 90일 |
| 13 | 오류·데이터 없음 응답 | 수집 기록과 원본 응답을 모두 저장한다 |

### 5. 설계서 "확인 못 함" 항목

이미 정해졌거나 확인할 필요가 없는 항목이다. 다시 묻지 않는다.

| # | 항목 | 결정 |
| --- | --- | --- |
| 16 | ECOS 연·분기·일, KOSIS 분기의 기간 형식 | #16 샘플로 설계서 5.1을 채운다(Issue #24) |
| 17 | 값이 실제로 고쳐지는지 | 확인할 필요 없다. 4번 규칙으로 충분하다 |
| 18 | 공공데이터포털 값의 단위 | 확인할 필요 없다. 9번에 따라 관리자가 단위를 넣는다 |
| 19 | KOSIS 분류가 2개 이상인 표 | 확인할 수 있는 표가 없어 다루지 않는다 |
| 20 | CPI, GDP, 외환보유액 | DB 설계를 위해 샘플을 더 받지 않는다 |
| 21 | 1000행이 넘는 응답 | 나누어 받는다(Go 수집) |
| 22 | 공공데이터포털 데이터 반영 시각 | 공공데이터포털도 같은 수집 시각을 따른다. 수집 시각은 관리자 화면에서 정한다(KEDP001-D018, D019) |

## 배경

KEDP001-D004에 따라 세 제공처의 실제 응답 샘플을 모은 뒤 DB 설계서 초안을 만들었다. 비교해 보니 세 곳 모두 한 행이 한 기간의 값이었고, 제공처별 차이는 계열을 가리키는 코드(통계 코드, 항목 코드, 분류, 종목 코드)에 모여 있었다. 공공데이터포털은 한 행에 값이 여러 개이고 단위 항목이 없으며, KOSIS 출생아 수 표는 단위가 분류 이름에 들어 있었다.

## 검토한 대안

- 제공처별 테이블
- 범용 테이블(지표 정의 + 관측값)
- 혼합(지표 정의에 제공처별 코드, 관측값은 공통, 원본 응답 별도)
- Staging-Result(원본 테이블과 정리된 결과 테이블로 나눔)

## 결정 이유

- 화면(대시보드, 상세)은 지표 하나의 시계열만 읽는다(KEDP001-D017). 관측값이 한 테이블이면 조회 API가 단순하다.
- 제공처 차이는 지표 정의에만 있으므로 그곳에 모은다. 지표 추가(KEDP001-D018)가 행 추가로 끝난다.
- Staging-Result 전체는 MVP에 무겁다. 원본 응답만 따로 남겨 재처리와 확인에 쓴다.
- 관측값 수가 적다(10개 지표, 하루 1회 수집). 성능 때문에 테이블을 나눌 이유가 없다.
- Rust가 정규화와 검증을 맡으므로(KEDP001-D002) 결과를 바로 DB에 쓰는 것이 단순하다.

## 영향

- Issue #24에서 설계서를 확정본으로 고치고 `b-sql-db/`에 migration을 만든다.
- `config/indicators.yaml`의 지표 정보는 지표 정의 테이블로 옮긴다(KEDP001-D021).
- 7번에 따라 Go가 받은 원본 응답을 Rust에 넘겨야 한다. `b-proto/` 변경이 필요하며 소유자 승인 뒤 바꾼다(KEDP001-D007).
- Rust가 멈추면 관측값 저장도 멈춘다. MVP에서는 받아들인다(KEDP001-D020).
- 6번의 90일 삭제를 실제로 돌리는 일은 MVP 이후에 한다. 그때까지 원본 응답은 쌓이기만 한다.

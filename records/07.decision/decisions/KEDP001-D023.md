# 배포: nginx가 화면과 /api를 받고, image는 dell-debian에서 만들어 SSH로 옮긴다

## 결론

1. **화면은 nginx가 내보낸다.** `npm run build`로 만든 정적 파일을 nginx container가 내보내고, `/api` 요청은 Go로 넘긴다. Vite는 개발할 때만 쓴다.
2. **실행 서버(macpro-debian)는 container 4개로 돈다.** nginx, Go, Rust, PostgreSQL이다. 바깥에는 nginx 포트만 연다. Go, Rust, PostgreSQL은 Docker 내부 network에서만 접속한다.
3. **image는 개발 서버(dell-debian)에서 하나씩 만든다.** 다른 무거운 작업(Claude Code 여러 개, 다른 Docker 작업)과 함께 돌리지 않는다.
4. **image는 SSH로 옮긴다.** `docker save`로 묶어 SSH로 보내고, macpro-debian에서 `docker load`로 받는다. registry는 쓰지 않는다.
5. **macpro-debian에는 소스를 두지 않는다.** image, compose 파일, `.env`, 관리자 계정 파일만 둔다. 키와 비밀번호는 image에 넣지 않는다(KEDP001-D002, D012).

## 배경

MVP 개발(사용자 화면, 관리자 화면)이 끝나면 개발 서버가 아닌 실행 서버에서 서비스만 돌려야 한다. KEDP001-D002는 Docker Compose 배포를, KEDP001-D020은 개발 서버에서 SSH로 실행 서버에 배포하는 것을 정했다. 화면을 누가 내보낼지, image를 어디서 만들어 어떻게 옮길지는 정하지 않았다.

개발 서버에서 Claude Code 2개와 Docker 작업 3개를 함께 돌렸을 때 서버가 멈춘 적이 있다. 하나씩 하면 문제가 없다.

## 검토한 대안

- 화면: nginx container / Go가 build 파일을 직접 내보냄
- image 만드는 곳: dell-debian / macpro-debian / GitHub Actions
- image 옮기는 방법: `docker save` + SSH / registry(GHCR)

## 결정 이유

- nginx는 지금 Vite proxy와 같은 구조(화면 + `/api` 넘기기)라서 화면 코드가 바뀌지 않는다. HTTPS도 나중에 nginx에서 붙일 수 있다.
- 개발 서버는 작업을 하나씩 하면 image를 만들 수 있다. 실행 서버는 서비스만 돌린다.
- SSH로 옮기면 registry, token 관리가 늘지 않고 KEDP001-D020과 맞는다.

## 영향

- 배포 작업에서 Dockerfile(Go, Rust, nginx + 화면 build)과 compose 파일을 만든다.
- **Go 허용 IP 검사를 고친다.** 지금 Go는 요청이 `127.0.0.1`에서 왔을 때만 `X-Forwarded-For`를 믿는다. container로 나누면 nginx 주소가 Docker 내부 주소가 되므로, 믿을 proxy 주소를 설정으로 받게 바꿔야 한다. 고치지 않으면 관리자 허용 IP 검사가 맞지 않는다(KEDP001-D018).
- nginx는 `X-Forwarded-For`에 실제 접속 주소를 넣어 Go로 넘긴다.
- HTTPS를 붙일 때 관리자 session cookie의 `Secure`를 켠다.
- 백업 스크립트와 crontab(KEDP001-D020)은 macpro-debian의 PostgreSQL container 기준으로 만든다.
- 처음 옮길 때 dell-debian의 DB(데이터 포함)도 macpro-debian으로 옮긴다. 순서는 소유자가 직접 진행한다.

# Go 수집 모듈 구조와 제공처를 붙이는 순서

## 결론

### 1. 용어

- **수집 모듈**: ECOS, KOSIS, 공공데이터포털을 부르는 쪽
- **조회 API**: 우리 화면에 데이터를 주는 REST API

이 결정은 수집 모듈에 대한 것이다.

### 2. 폴더 구조

```text
b-go-end/
├── go.mod
├── cmd/
│   └── server/              프로그램 시작점
├── config/
│   └── indicators.yaml      지표 정보 (DB가 생기기 전까지 임시)
└── internal/
    ├── config/              공통: .env에서 키 읽기, 설정 읽기
    ├── fetch/               공통: 요청 보내기, 시간 제한, 키 가리기, 응답 저장
    └── source/
        ├── source.go        공통 약속: 지표 정보를 받아 원본 응답을 돌려준다
        ├── ecos/            1단계
        ├── kosis/           2단계
        └── data_go_kr/      3단계
```

- 지표 정보(제공처, 통계 코드, 항목 코드, 주기 등)는 코드에 넣지 않고 `config/indicators.yaml`에 둔다. DB가 생기면 DB로 옮긴다(KEDP001-D018).
- 응답 샘플은 `samples/ecos/`, `samples/kosis/`, `samples/data-go-kr/`에 저장한다.

### 3. 처음부터 공통으로 두는 것

어느 제공처든 같은 것은 1단계부터 공통 자리(`internal/config`, `internal/fetch`)에 만든다.

- `.env`에서 키 읽기
- 요청 보내기와 시간 제한
- 키 가리기: 기록하는 요청 주소의 키 자리를 `***`로 바꾼다 (KEDP001-D012의 2겹)
- 받은 응답 저장

### 4. 제공처를 붙이는 순서

| 단계 | 하는 일 | 끝났다는 기준 |
| --- | --- | --- |
| 1 | 공통 최소 + ECOS | ECOS 샘플 저장, 키가 가려짐, 테스트 통과 |
| 2 | KOSIS + 공통 다듬기 | ECOS·KOSIS 테스트 모두 통과 |
| 3 | 공공데이터포털 + 공통 다듬기 | 세 제공처 테스트 모두 통과 |

- 새 제공처를 붙이다가 앞의 것과 겹치는 부분을 찾으면, 공통으로 빼고 **앞의 제공처도 그 자리에서 바로** 공통을 쓰게 고친다.
- 마지막에 한꺼번에 다시 연결하는 단계는 두지 않는다.

### 5. 테스트

- 받아 둔 응답 샘플로 "응답을 제대로 읽는지" 테스트한다. 테스트할 때 실제 API를 부르지 않는다.
- 단계가 끝날 때마다 앞의 제공처 테스트도 모두 통과해야 한다.

## 배경

수집 모듈을 기준금리 하나만 보고 만들면 다른 제공처를 붙일 때 다시 고쳐야 한다. 반대로 공통 모듈을 먼저 다 만들면, 실제 응답을 보지 않은 채 추측으로 만들게 된다(KEDP001-D004와 같은 이유). 제공처마다 키를 넣는 위치, 응답 모양, 오류 코드가 다르다.

## 검토한 대안

- 공통 수집 모듈을 먼저 만든다
- 세 제공처를 따로 만든 뒤 마지막에 공통으로 합친다
- 확실히 같은 것만 먼저 공통으로 두고, 제공처를 하나씩 붙이며 공통을 다듬는다

## 결정 이유

- 실제로 붙여 보면서 겹치는 부분을 확인한 뒤 공통으로 만든다.
- Agent는 처음 만든 코드를 본보기로 따라 한다. 첫 구현에 공통 틀이 있어야 다음 제공처도 같은 틀로 만든다.
- 따로 만든 뒤 마지막에 합치면 동작하는 코드 여러 개를 한꺼번에 고쳐야 해서 실수가 늘고 확인할 양이 커진다.
- 샘플 테스트가 있으면 공통을 다듬다가 앞의 제공처를 망가뜨렸는지 바로 알 수 있다.

## 영향

- 1단계 작업에 공통 최소 부분과 ECOS가 함께 들어간다.
- 세 제공처의 샘플이 모이면 DB 설계(KEDP001-D004)의 근거가 된다.

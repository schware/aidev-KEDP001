# 배포 방식 세 가지: dell-debian build(A)에 GitHub build + GHCR(B), GitHub build + artifact(C)를 더한다

## 결론

1. **배포 방식을 세 가지로 둔다.** 배포할 때마다 소유자가 하나를 고른다. 지금 방식(A)이 기본이다.

   | | A. 지금 | B. GitHub build + GHCR | C. GitHub build + artifact |
   | --- | --- | --- | --- |
   | image 만드는 곳 | dell-debian(`deploy/build.sh`) | GitHub Actions | GitHub Actions |
   | 옮기는 방법 | `docker save` → SSH → `docker load`(`deploy/send.sh`) | GHCR에 push, macpro-debian이 `docker pull` | image 묶음을 artifact로 올리고, dell-debian이 받아 SSH → `docker load` |
   | 보관 | 서버에 남은 image | GHCR에 최근 5개 버전 | artifact 14일, 운영 중 + 새 버전 2개 |
   | 언제 쓰나 | 지금처럼 개발 서버에서 바로 | **되돌리기를 보관 정책으로 관리할 때.** 최근 5개 버전을 남겨 두고 그 안에서 되돌린다 | **QA까지 확정하고 배포할 때.** 되돌리기를 최소로 하고, 14일 안에 확정한다 |

2. **세 방식 모두 tag는 같다.** build한 commit의 git short hash 7자리다(예: `c1bd8ab`). 같은 commit이면 어느 방식으로 만들어도 tag가 같다.
3. **GitHub build는 손으로 실행할 때만 돈다**(workflow_dispatch). main의 commit만 build한다. main에 merge할 때마다 image를 만들지 않는다.
4. **B의 image 이름은 `ghcr.io/schware/kedp-go`, `kedp-rust`, `kedp-nginx`다.** GHCR package는 공개로 한다. 그래서 macpro-debian은 로그인과 token 없이 pull한다.

   **B는 최근 5개 버전만 보관한다.** 지금 운영 중인 버전과 그 전 4개 버전이다. 무한정 보관하는 것은 관리할 것만 늘고 쓸 일이 없다. 새 버전을 push한 뒤 workflow가 image마다 최근 5개를 남기고 나머지 버전을 지운다. macpro-debian의 B image도 같은 5개 tag만 남긴다.
5. **C는 14일 확정 기간을 둔다.** artifact는 14일 뒤 사라지는 것이 목적이다. 그 안에 QA와 확정을 끝낸다. 14일이 지난 버전으로는 되돌리지 않고, 문제가 생기면 고친 commit으로 새로 build한다(앞으로 가기). artifact 말고 다른 곳에 사본을 남기지 않는다.

   **C는 두 버전(지금 운영 중 + 새 버전)이 살아 있는 상태로 운영한다.**
   - 새 버전을 build하기 전에, 지금 운영 중인 버전(같은 commit)을 한 번 다시 build해 artifact를 새로 올린다. 그러면 되돌릴 버전의 14일이 다시 시작된다.
   - 그다음 새 버전을 build해 배포한다. 배포한 뒤에는 두 artifact가 모두 14일 안에 있다.
   - macpro-debian에도 C의 image는 이 두 tag만 남기고 그보다 오래된 것은 지운다.
   - 같은 commit을 다시 build하면 tag와 소스는 같다. 다만 base image가 그사이 갱신되었으면 image 안의 OS 파일은 조금 다를 수 있다.

   옮길 때는 dell-debian(`gh` 로그인됨)을 통로로만 쓰고, 받은 파일은 보낸 뒤 바로 지운다. macpro-debian에는 token을 두지 않는다.
6. **compose는 image 이름 앞에 붙일 주소를 변수로 받는다**(`KEDP_IMAGE_PREFIX`). 비우면 A, C와 같고, `ghcr.io/schware/`를 넣으면 B다.
7. **image 안의 내용은 세 방식 모두 같다.** 같은 Dockerfile과 build context(`proto`, `nginx-conf`)를 쓴다. 키와 비밀번호는 image에 넣지 않는다(KEDP001-D002, D012).
8. **비용이 들지 않게 한다.** 공개 저장소와 공개 package의 무료 범위 안에서만 쓴다. B를 처음 실행한 뒤 GitHub Billing에서 Actions와 Packages 사용 비용이 0인지 확인한다.
9. **배포는 PR 중심으로 한다. PR로 main에 merge된 commit만 배포하고, branch별 배포는 하지 않는다.** 세 방식 모두 같다.
   - 배포할 수 있는 것: PR에서 CI(test, secret-scan)가 통과하고 merge된 commit
   - main 보호 설정을 켠다(소유자). main에 직접 push를 막고, PR과 CI 통과를 merge 조건으로 둔다. 저장소가 공개라 무료로 쓸 수 있다(KEDP001-D011 "공개로 바꿀 때 main 보호 설정"). 이 설정이 있으면 main의 모든 commit이 곧 PR을 거친 commit이다.
   - B, C: workflow는 실행할 commit이 main에 있고 merge된 PR에 연결된 commit인지 확인한다. 아니면 멈춘다. 실행 요약에 PR 번호를 적는다.
   - A: `deploy/build.sh`는 지금 commit이 `origin/main`에 없거나 commit하지 않은 변경이 있으면(`-dirty`) 멈춘다. 시험용으로 branch image를 만들 때만 `--allow-branch`를 붙이고, 그 image는 배포하지 않는다.
   - tag는 main commit의 hash라서, tag만 보고 main 어디에서 만든 버전인지 알 수 있다.

## 배경

KEDP001-D023은 image를 dell-debian에서 만들어 SSH로 옮기고, registry는 쓰지 않기로 정했다. 이 방식은 잘 돌고 있다. 다만 dell-debian에서 Rust를 compile하는 동안 다른 작업을 멈춰야 한다.

MVP와 포트폴리오 정리(2026-11-08)가 끝났다. 이제 같은 서비스를 다른 방식으로도 배포해 보고 비교하려 한다. 저장소는 공개로 바뀌었고(D011), PR마다 CI(test)가 돈다.

## 검토한 대안

- 배포 방식: A만 유지 / B만으로 바꾸기 / **A를 기본으로 두고 B, C를 더하기**(고름)
- B의 보관: 무한정 / **최근 5개 버전**(고름: 무한정은 관리할 것만 늘고 쓸 일이 없다)
- B의 package: **공개**(고름) / 비공개 + macpro-debian에 읽기 token(고르지 않음: token 관리가 늘고, 무료 한도를 넘으면 비용이 생긴다)
- C의 보관: 오래 보관 / **14일 뒤 사라짐**(고름: 확정 기간을 강제한다. 오래 보관하며 되돌리는 쓰임은 B가 맡는다)
- C의 artifact 받는 곳: **dell-debian을 통로로만**(고름) / macpro-debian에서 직접(고르지 않음: 실행 서버에 token 필요)
- GitHub build 시점: main push마다 / git tag push마다 / **손으로 실행할 때만**(고름)

## 결정 이유

- A는 잘 돌고 있어 버릴 이유가 없다. B, C를 더해도 A의 순서는 바뀌지 않는다.
- 배포를 PR 중심으로 묶으면 배포한 버전마다 PR(무엇을, 왜 바꿨는지)과 CI 결과가 함께 남는다. 배포가 "코드를 서버에 올리는 일"이 아니라 검토를 거친 변경을 내보내는 절차가 된다.
- branch별 배포를 막는다. branch image가 운영에 올라가면 main에 없는 코드가 돌게 되고, 무엇이 운영 중인지 기록으로 추적할 수 없다. 2026-11-08에는 pull하지 않은 채 PR branch에서 `deploy/build.sh`를 실행해 그 commit(`ff670bf`)으로 image가 만들어진 일이 있었다.
- tag가 같으면 세 방식의 결과를 비교할 수 있다. 또 한 방식에 문제가 생기면 같은 tag로 다른 방식을 써서 되돌릴 수 있다.
- 저장소가 공개이고 image에는 키가 없다. 그래서 GHCR package를 공개해도 새로 드러나는 것이 없다. 공개로 하면 실행 서버에 token을 둘 필요가 없다.
- B와 C는 쓰임이 다르다. B는 보관 정책을 분명히 두고 지난 버전으로 되돌릴 수 있게 한다. C는 QA까지 확정한 뒤 배포해 되돌리기를 최소로 한다. 많은 개발 조직에서 배포는 2주 안에 확정되고, 그보다 늦게 되돌린다면 그것 자체가 이상 신호다. artifact가 14일 뒤 사라지는 것이 이 원칙을 지키게 한다.
- artifact는 어떤 GitHub 계정이든 로그인만 하면 받을 수 있다(특정 계정만 받는 것이 아니다). 로그인이 필요한 것은 받는 도구의 조건이지 보호 수단이 아니다. 이미 로그인된 dell-debian을 통로로 쓰면 실행 서버에 비밀을 늘리지 않는다. 받은 파일을 바로 지우므로 사본도 남지 않는다.
- 손으로 실행하면 배포하기로 한 commit만 image가 된다. GHCR와 artifact 저장 공간도 적게 쓴다.
- 공개 저장소와 공개 package는 GitHub Actions 실행과 GHCR 저장·내려받기에 비용이 들지 않는다. 비공개로 하면 무료 한도(저장 500MB 등)를 넘을 때 비용이 생긴다. KEDP image 3개는 tag 하나에 약 125MB라 비공개면 tag 몇 개로 한도를 넘는다(요금 기준은 2026-11 GitHub 안내 기준, 바뀔 수 있다).

## 영향

### 공통

- `deploy/compose.yaml`: go, rust, nginx의 image를 `${KEDP_IMAGE_PREFIX:-}kedp-go:${KEDP_IMAGE_TAG}` 꼴로 바꾼다. 비어 있으면 지금과 같다.
- `deploy/.env.example`: `KEDP_IMAGE_PREFIX=`를 더한다.
- GitHub build는 같은 commit을 두 번 build해도 같은 tag가 된다. 다시 실행하면 덮어쓴다.
- 문서: `docs/docker-build.md`에 "세 가지 배포 방식" 장을 더한다. `docs/docker-deploy.md` 7장에서 B, C의 배포 순서를 안내한다.

### B. GitHub build + GHCR

- workflow `.github/workflows/build-ghcr.yml`(workflow_dispatch)
  - 권한: `contents: read`, `packages: write`. 로그인은 `GITHUB_TOKEN`으로 한다
  - main이 아닌 ref로 실행하면 멈춘다
  - image 3개를 build해 `ghcr.io/schware/kedp-{go,rust,nginx}:<tag>`로 push한다. `latest` tag는 만들지 않는다
  - image에 저장소 label(`org.opencontainers.image.source`)을 붙여 package가 저장소에 연결되게 한다
  - push한 뒤 image마다 최근 5개 버전만 남기고 나머지를 지운다(권한 `packages: write`로 충분하다)
  - 마지막에 tag와 지운 버전을 실행 요약(job summary)에 적는다
- 소유자가 한 번 할 일: 첫 push 뒤 GitHub에서 package 3개를 공개(Public)로 바꾼다. 그다음 Billing에서 비용이 0인지 확인한다.
- 배포(macpro-debian): `.env`에 `KEDP_IMAGE_PREFIX=ghcr.io/schware/`, `KEDP_IMAGE_TAG=<tag>` → `docker compose pull` → `docker compose up -d`

### C. GitHub build + artifact

- workflow `.github/workflows/build-artifact.yml`(workflow_dispatch)
  - 권한: `contents: read`(artifact 올리기는 따로 권한이 필요 없다)
  - main이 아닌 ref로 실행하면 멈춘다
  - image 3개를 `kedp-{go,rust,nginx}:<tag>` 이름으로 build한다. 그다음 `docker save | gzip`으로 `kedp-images-<tag>.tar.gz` 하나로 묶는다
  - artifact 이름은 `kedp-images-<tag>`, 보관 14일
  - 마지막에 tag와 artifact 이름을 실행 요약에 적는다
- `deploy/send-artifact.sh <SSH Host> <tag>`(dell-debian): `gh run download`로 artifact를 받아 SSH로 macpro-debian에 `docker load`한다. 받은 파일은 성공·실패와 상관없이 지운다. artifact가 이미 사라졌으면 "14일이 지났다, 새로 build하라"고 알리고 멈춘다.
- 배포 순서(C)
  1. GitHub: 지금 운영 중인 commit으로 workflow 실행(되돌릴 버전 artifact 새로 올리기)
  2. GitHub: 새 commit으로 workflow 실행
  3. dell-debian: `deploy/send-artifact.sh macpro-debian <새 tag>`
  4. macpro-debian: `KEDP_IMAGE_PREFIX`는 비우고 `KEDP_IMAGE_TAG=<새 tag>` → `docker compose up -d`(A와 같다)
  5. macpro-debian: C의 image는 두 tag(새 tag, 직전 tag)만 남기고 지운다
- workflow는 실행할 commit(ref)을 입력으로 받는다. 비우면 main의 최신 commit이다. 입력한 commit은 main에 있는 것이어야 한다.

### 바뀌지 않는 것

- A의 순서와 `deploy/send.sh`. `deploy/build.sh`는 main 검사(결론 9)만 더한다
- Dockerfile, `.dockerignore`, 실행 서버의 `.env` 키, DB migration 순서(docs/docker-deploy.md 7장)
- KEDP001-D023의 나머지 결론(nginx, container 4개, macpro-debian에 소스를 두지 않음). D023 결론 4 "registry는 쓰지 않는다"는 B에 한해 이 결정으로 바꾼다.

## 작업 나누기

1. B: compose 변수, `deploy/build.sh` main 검사, GHCR workflow, 문서. **첫 tag의 image 3개가 GHCR에 올라가는 것까지** 한다.
2. C: artifact workflow, `send-artifact.sh`, 문서. **첫 tag의 artifact가 만들어지고 dell-debian에서 받아지는 것까지** 한다.

실행 서버를 B, C로 실제 바꿔 띄우는 것은 소유자가 한다.

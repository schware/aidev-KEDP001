# 로그 규칙: 화면 동작부터 Go, Rust까지 기본 동작을 같은 형식으로 남긴다

## 결론

### 1. 어디에 남기나

- 모든 container는 로그를 stdout/stderr로만 내보낸다. 파일로 따로 쓰지 않는다. Docker가 받아 저장하고 `docker compose logs`로 본다(지금과 같다).
- `deploy/compose.yaml`의 go, rust, nginx, postgres에 같은 `logging` 설정을 둔다. container 하나당 10 MB 파일 5개, 최대 약 50 MB다. 그보다 오래된 줄은 사라진다.

  ```yaml
  logging:
    driver: json-file
    options: { max-size: "10m", max-file: "5" }
  ```

- 로그는 운영 확인용이다. 통계(방문자 수 등)는 지금처럼 DB에 두고, 로그로 셈하지 않는다.

### 2. 한 줄 형식

모든 component가 같은 `key=value` 한 줄 형식을 쓴다. 값에 공백이 있으면 큰따옴표로 감싼다.

```text
time=2026-11-24T06:00:01.123+09:00 level=INFO comp=go event=http.request req=4f1c… method=GET path=/api/indicators status=200 ms=12
time=2026-11-24T06:00:03.456+09:00 level=INFO comp=rust event=process.page run=812 indicator=cpi page=1 status=SUCCESS inserted=0 updated=1
time=2026-11-24T09:12:40.001+09:00 level=INFO comp=web event=ui.card_open req=9a0b… page=/ indicator=cpi
```

| key | 뜻 | 반드시 |
| --- | --- | --- |
| `time` | Asia/Seoul, 밀리초까지(RFC 3339) | 예 |
| `level` | `DEBUG`, `INFO`, `WARN`, `ERROR`(3장) | 예 |
| `comp` | `nginx`, `web`(화면이 보낸 동작), `go`, `rust` | 예 |
| `event` | 아래 4장의 이벤트 이름. `영역.동작` 꼴, 영어 소문자 | 예 |
| `req` | 요청 ID(5장). HTTP 요청에서 생긴 줄에만 | 해당 시 |
| `run` | 수집 실행 ID(`collection_run.id`). 수집에서 생긴 줄에만 | 해당 시 |
| `err` | 오류 내용. `level`이 `WARN`, `ERROR`일 때 | 해당 시 |

- 구현: Go는 표준 라이브러리 `log/slog`의 TextHandler를 쓴다. Rust는 새 의존성 없이 같은 꼴을 찍는 작은 함수(또는 macro)를 둔다. 기존 `log.Printf`, `eprintln!`은 이 형식으로 바꾼다.
### 3. level 기준

모든 줄에 `level`이 반드시 있고, 값은 아래 네 가지뿐이다. `FATAL`, `TRACE`, `NOTICE` 같은 다른 이름은 쓰지 않는다. 대문자로 쓰고, 줄의 두 번째 칸(`time` 다음)에 둔다.

| level | 뜻 | 사람이 할 일 | 예 |
| --- | --- | --- | --- |
| `DEBUG` | 개발 중 흐름을 따라가기 위한 자세한 기록. 운영 기본값에서는 찍지 않는다 | 없음 | 수집 시각 확인 tick(30초마다), 제공처 페이지별 요청 상세, Rust 처리 단계별(검증·읽기·저장) 소요 시간, 화면 이벤트 원본 칸 |
| `INFO` | 정상 동작. 일어나야 할 일이 일어났다 | 없음 | 서버 켜짐·꺼짐, 요청 처리(2xx·3xx·404, 로그인 상태 401), 수집 시작·끝(모두 성공), 지표 하나 성공, 관리자 로그인·로그아웃·변경, 화면 동작 |
| `WARN` | 하나가 실패했거나 이상하지만 서버는 계속 정상이다. 스스로 넘어가거나 바깥(사용자, 제공처) 탓이다 | 하루 한 번 훑어본다. 같은 줄이 반복되면 확인한다 | 그 밖의 4xx, 관리자 로그인 실패, 허용 IP 거부, 제공처가 오류 응답을 줌, 지표 하나 수집 실패, 일부 지표만 실패한 수집, 응답 단위 바뀜, 화면 이벤트 버림(`ui.dropped`), 하루 방문자 상한 도달, 화면의 API 호출 실패(`ui.error`) |
| `ERROR` | 서버 쪽 문제로 기능이 실패했다 | 바로 확인한다 | 5xx, DB 접속·쿼리 실패, Rust 연결 실패(gRPC 오류), 시작할 때 Rust Check 실패, 수집 전체 실패(`ErrProcessor` 등), 설정 오류로 멈춤 |

- **멈추는 오류**: 프로그램이 멈출 때는 `level=ERROR`로 이유를 한 줄 남기고, 이어서 `event=server.stop reason=…`을 남긴다. 따로 `FATAL`을 두지 않는다.
- **한 사건에 한 level**: 같은 실패를 여러 층에서 겹쳐 `ERROR`로 찍지 않는다. 실패를 처리하고 결과를 결정하는 곳(Go는 handler·수집 끝, Rust는 gRPC 응답 직전)에서 한 번만 찍는다. 아래 층은 `DEBUG`로만 남긴다.
- **HTTP 응답 코드 → level** (Go `http.request`, nginx access 모두 같다)

  | 응답 | level |
  | --- | --- |
  | 2xx, 3xx, 404, `GET /api/admin/session`의 401(로그인 안 함) | `INFO` |
  | 그 밖의 4xx | `WARN` |
  | 5xx | `ERROR` |

- **화면 이벤트의 level은 Go가 정한다.** 화면이 보낸 값에 level이 있어도 쓰지 않는다. `ui.error`만 `WARN`이고 나머지 `ui.*`는 `INFO`다.

**보이는 level 정하기(`KEDP_LOG_LEVEL`)**

- `.env`의 `KEDP_LOG_LEVEL`(`DEBUG`, `INFO`, `WARN`, `ERROR`)로 정하고, 그 level 이상만 찍는다. 기본값은 `INFO`다. Go와 Rust가 같은 값을 읽는다(compose에서 rust에도 이 값 하나만 넘긴다).
- 잘못된 값이면 `INFO`로 두고, 시작할 때 `level=WARN event=config.log_level value=…`를 한 줄 남긴다. 멈추지 않는다.
- 시작할 때 `event=server.start`에 지금 level을 `log_level=INFO`처럼 함께 남긴다.
- 바꾸려면 `.env`를 고치고 container를 다시 띄운다(`docker compose up -d go rust`). 실행 중에 바꾸는 기능은 두지 않는다.
- nginx는 `map`으로 응답 코드에서 `level`을 만들어 access 줄에 넣는다. nginx 자체 오류 기록(error log)은 nginx 형식(`[error]`, `[warn]`) 그대로 두고, `KEDP_LOG_LEVEL`을 따르지 않는다.

**level로 골라 보기**

```bash
docker compose logs --since 24h go rust | grep -E 'level=(WARN|ERROR)'   # 확인할 것만
docker compose logs --since 1h go | grep 'level=ERROR'                    # 바로 볼 것
docker compose logs -f go rust nginx | grep -v 'level=DEBUG'               # DEBUG를 켰을 때 빼고 보기
```

### 4. 남기는 기본 동작

`level` 칸은 3장 기준을 따른다. 조건에 따라 달라지면 조건을 적었다.

| comp | event | 언제 | 주요 key | level |
| --- | --- | --- | --- | --- |
| nginx | (access) | 요청마다 | `req`, method, path, status, ms | 응답 코드로(3장 표) |
| web | `ui.page_view` | 화면 열림(메인, 상세, 관리자 각 화면) | `page` | INFO |
| web | `ui.card_open` | 메인에서 카드를 눌러 상세로 이동 | `indicator` | INFO |
| web | `ui.related_open` | 상세 화면에서 관련 지표를 누름 | `indicator`, `from` | INFO |
| web | `ui.admin_action` | 관리자 화면에서 저장·추가·로그인·로그아웃 버튼을 누름 | `action` | INFO |
| web | `ui.error` | 화면에서 API 호출이 실패함 | `path`, `status` | WARN |
| go | `server.start`, `server.stop` | 켜짐(`log_level`), 꺼짐(`reason`) | `log_level`, `reason` | INFO. 오류로 멈추면 그 앞에 ERROR 한 줄 |
| go | `processor.check` | 시작할 때 Rust Check 결과 | `ok` | 성공 INFO, 실패 ERROR |
| go | `http.request` | `/api/` 요청마다(끝날 때 한 줄) | `req`, method, path, status, ms | 응답 코드로(3장 표) |
| go | `schedule.next` | 다음 수집 시각 | `at` | INFO |
| go | `schedule.tick` | 수집 시각이 지났는지 확인(30초마다) | `next` | DEBUG |
| go | `collect.start`, `collect.finish` | 수집 전체 시작·끝 | `run`, `trigger`, 결과 요약 | 시작 INFO. 끝: 모두 성공 INFO, 일부 실패 WARN, 전체 실패 ERROR |
| go | `collect.indicator` | 지표 하나 수집 끝 | `run`, `indicator`, status, code, rows | 성공 INFO, 실패 WARN |
| go | `fetch.request` | 제공처 요청 한 번(주소는 키를 `***`로 가림) | `run`, `source`, page, status, ms | 성공 DEBUG, 실패(시간 초과, 2xx 아님) WARN |
| go | `admin.login`, `admin.logout`, `admin.audit` | 관리자 로그인·로그아웃·변경(지금의 `admin audit:`) | `account`, 바꾼 것 | 로그인·로그아웃·변경 INFO, 로그인 실패·허용 IP 거부 WARN |
| rust | `server.start`, `server.stop` | 켜짐, 꺼짐 | `addr`, `log_level` | INFO. 오류로 멈추면 그 앞에 ERROR 한 줄 |
| rust | `grpc.check` | Check 결과 | `ok` | 성공 DEBUG(Go가 INFO로 남긴다), 실패 ERROR |
| rust | `process.page` | ProcessPage 결과(지금 줄과 같은 값) | `run`, `indicator`, page, status, 건수 | `SUCCESS` INFO, 제공처 오류 판정 WARN, gRPC 오류 ERROR |
| rust | `process.step` | 처리 단계(검증, 지표 읽기, 응답 읽기, 저장)별 소요 시간 | `run`, `indicator`, step, ms | DEBUG |
| rust | `source_unit.changed` | 응답 단위가 바뀜(지금과 같다) | `indicator`, old, new | WARN |

- 이 목록에 없는 이벤트를 더할 때는 이 표에 먼저 적는다(명세 갱신).
- 화면은 이 표의 `ui.*` 이름만 보낸다(`ui.dropped`는 Go가 만드는 줄, WARN). Go는 목록에 없는 이름을 버린다.

### 5. 요청 ID로 한 동작을 따라간다

- nginx가 요청마다 `$request_id`를 만들어 `X-Request-ID` 헤더로 Go에 넘기고, 자기 access 로그에도 같은 값을 `req`로 남긴다.
- Go는 받은 `X-Request-ID`를 그 요청의 모든 줄에 `req`로 붙이고, 응답 헤더에도 돌려준다. 헤더가 없으면(개발 중 Vite) Go가 만든다.
- 화면이 보내는 `ui.*` 이벤트도 같은 방식으로 `req`를 받는다. 그래서 "버튼 클릭 → API 요청 → 응답"을 시각과 `req`로 이어 볼 수 있다.
- 수집은 HTTP 요청이 아니므로 `run`(수집 실행 ID)으로 Go와 Rust 줄을 잇는다. Go가 ProcessPage에 이미 `run_id`를 넘기므로 `b-proto/` 메시지는 바꾸지 않는다.

### 6. 화면 동작을 서버로 보내는 API

```text
POST /api/events     {"event": "ui.card_open", "page": "/", "indicator": "cpi"}
```

- 화면 동작은 서버로 보낸다. 브라우저에서 일어나는 클릭은 이 API로만 서버 로그에 남는다.
- 인증 없음. 응답은 언제나 204(본문 없음)다. 잘못된 요청도 화면에 오류를 보이지 않는다.
- 본문 1 KiB까지. `event`는 4장의 `ui.*` 목록만, 나머지 칸은 정해진 이름과 짧은 값(지표 id, 화면 경로)만 받는다. 그 밖은 버린다.
- 로그가 넘치지 않도록 Go 전체에서 초당 상한을 둔다(예: 초당 50줄). 넘으면 버리고, 1분에 한 번 `ui.dropped count=…`를 남긴다.
- 화면은 `navigator.sendBeacon`(안 되면 `fetch` + `keepalive`)으로 보내고, 실패해도 다시 보내지 않는다. 화면 동작을 막지 않는다.
- DB에는 저장하지 않는다. 로그 한 줄로만 남는다.

### 7. 남기지 않는 것

- API 키, 비밀번호, cookie·session 값, DB 비밀번호. 제공처 요청 주소는 키 자리를 `***`로 가린다(지금과 같다).
- 제공처 응답 본문, 요청 본문 전체. 관리자 변경은 "무엇을 바꿨는지"만 남긴다(지금의 `admin audit:`).
- 일반 사용자의 접속 주소, User-Agent, 방문자 hash(40.api 6.1 "남기지 않는 것"). nginx access 로그도 이 규칙을 따른다: `$remote_addr`, `$http_user_agent`, `$http_x_forwarded_for`를 빼는 `log_format`을 쓴다.
- 예외: 관리자 API의 로그인 실패, 허용 IP 거부는 접속 주소를 남긴다(지금과 같다). 허용 IP 안에서만 오는 요청이고, 무차별 로그인 시도를 알아보는 데 필요하다. 일반 사용자 요청에는 이 예외를 쓰지 않는다.

## 배경

- 지금 Go와 Rust는 일부 동작만 로그로 남긴다. Go는 `log.Printf`, Rust는 `eprintln!`로 형식이 제각각이고, Rust 줄에는 시각이 없다. 요청마다 남는 줄이 없어 "누가 무엇을 눌렀고 서버가 어떻게 답했는지"를 따라갈 수 없다. 화면(f-ts-end) 동작은 어디에도 남지 않는다.
- `deploy/compose.yaml`에 `logging` 설정이 없어 Docker 기본값이면 로그 파일이 크기 제한 없이 커진다.
- nginx image(`nginx:stable-alpine`)의 기본 access 로그는 접속 주소와 User-Agent를 남긴다. 이것은 40.api 6.1 "접속 주소, User-Agent는 서버 기록 어디에도 남기지 않는다"와 어긋난다(이 결정과 상관없이 고칠 문제다).
- 소유자 요청(2026-11-24): "버튼 클릭부터 go, rust에 대한 로그를 전체적으로 다 관리해서 남겨 달라."

## 검토한 대안

- 형식: 지금처럼 자유 문장 / **`key=value` 한 줄**(고름) / JSON 한 줄(고르지 않음: `docker compose logs`로 사람이 읽기 어렵다. `grep`으로 찾기는 `key=value`도 충분하다)
- Rust 구현: `tracing` + `tracing-subscriber` 의존성 추가 / **의존성 없이 작은 함수**(고름: 찍는 곳이 몇 군데뿐이고 build 시간·크기를 늘리지 않는다)
- 화면 동작: 남기지 않음(API 요청 로그로만 추정) / **허용 목록만 `POST /api/events`로 보냄**(고름) / 외부 분석 서비스(고르지 않음: 외부로 사용자 정보가 나간다, 비용)
- 보관 크기: **container당 10 MB × 5개**(고름) / 더 크게 / Docker 기본값(고르지 않음: 제한이 없어 macpro-debian 디스크를 채울 수 있다)
- 관리자 로그인 실패의 접속 주소: **남김**(고름) / 남기지 않음(고르지 않음: 로그인 시도를 알아볼 수 없다)
- 저장: **Docker 로그**(고름) / 파일 volume / DB 테이블(고르지 않음: 관리할 것이 늘고, 로그는 오래 둘 필요가 없다)

## 결정 이유

- 같은 형식이면 `docker compose logs | grep event=collect` 한 번으로 Go와 Rust 줄을 함께 볼 수 있다.
- `req`, `run` 두 값만으로 화면 클릭 → Go → Rust를 이어 볼 수 있고, `b-proto/`를 바꾸지 않는다.
- 화면 이벤트를 허용 목록과 초당 상한으로 묶으면, 인증 없는 API라도 로그를 함부로 채울 수 없다.
- 개인정보 규칙(40.api 6.1)을 로그에도 똑같이 적용해, 방문자 수 기능의 약속을 지킨다.

| 폴더 | 할 일 | 담당 |
| --- | --- | --- |
| `b-go-end/` | `log/slog` 공통 logger, `KEDP_LOG_LEVEL`, `http.request` middleware, `X-Request-ID`, `POST /api/events`, 기존 줄을 새 형식으로, `server.stop` | Go |

| `specification/40.api/` | `POST /api/events` 장, 1장에 `X-Request-ID` | Common |
| `docs/docker-deploy.md` | 로그 보는 법 표를 새 `event` 이름으로 | Common |

- 운영 중 로그 양: 요청 로그와 화면 이벤트가 늘어난다. container당 50 MB 상한이므로 오래된 줄부터 사라진다. 오래 보관해야 하는 것은 로그가 아니라 DB(`collection_run` 등)에 있다.
- 기존 로그를 `grep`하던 안내(`grep collection`, `"server started"`)는 새 이름으로 바뀐다. 배포 문서를 함께 고친다.

## 작업 나누기

1. Go: logger·형식·요청 로그·요청 ID·`server.stop` (화면 이벤트 API 제외)
2. Rust: 로그 함수와 기존 줄 바꾸기
3. deploy: nginx `log_format`, `X-Request-ID`, compose `logging`(개인정보 어긋남을 먼저 고친다)
4. Go + 명세: `POST /api/events`
5. TypeScript: `ui.*` 이벤트 보내기
6. 문서: 배포 안내의 로그 보는 법

1~3은 서로 기다리지 않는다. 5는 4 다음이다.

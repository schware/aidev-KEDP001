# Git 작업 방식

## 결론

KEDP는 직접 `main` 브랜치에서 작업하지 않는다.
모든 작업은 개별 브랜치에서 진행하고 Pull Request(PR)를 통해 병합한다.
최종 병합은 프로젝트 소유자가 수행한다.
작업마다 `담당/이슈번호-작업내용` branch를 만들어 PR로 합친다. commit, push, PR, merge는 사람이 한다. 사람이 요청하면 Agent가 PR 생성까지 할 수 있고, merge는 하지 않는다. merge는 squash로 하고, PR 설명에 `Closes #이슈번호`를 넣는다.

## 배경

프로젝트 규모가 작더라도 변경 이력을 명확히 관리할 필요가 있다.

작업 단위별 변경 내역을 기록하고 검토 절차를 유지하여 실수와 충돌을 줄인다.

초기 단계부터 팀 개발 방식을 적용하여 프로젝트 운영 기준을 정착시킨다.

## 검토한 대안

- commit: Agent도 / 사람만
- 반영: main 직접 / branch + PR
- 도구: GitHub Desktop / gh와 GitHub 웹

## 결정 이유

### Branch + PR

- 작업 단위 분리 가능
- 검토 과정 유지 가능
- 변경 이력 추적 가능

### 프로젝트 소유자 Commit

- 코드 검토 과정 확보
- 변경 사항 최종 확인 가능
- 실수 방지

### Squash Merge

- Commit History 단순화
- 작업 단위 중심 기록 유지
- 이력 관리 용이

---

## Branch 규칙

Branch 이름은 다음 형식을 따른다.

```text
{담당영역}/{이슈번호}-{작업내용}
```

예시

```text
go/12-ecos-collector

rust/15-normalizer

ts/21-dashboard-card

db/30-schema-design

common/40-decision-update
```

---

## Pull Request 규칙

PR은 반드시 이슈와 연결한다.

예시

```text
Closes #12
```

PR 설명에는 다음 내용을 포함한다.

```text
목적

변경 내용

영향 범위

확인 방법
```

---

## Merge 규칙

병합은 Squash Merge를 사용한다.

```text
Feature Branch

↓

Pull Request

↓

검토

↓

Squash Merge

↓

Main
```

직접 Main Push는 허용하지 않는다.

---

## Agent 작업 원칙

Agent는 다음 작업을 수행할 수 있다.

```text
코드 생성

문서 작성

PR 초안 작성

Commit 메시지 제안
```

사용자의 요청이 있을 경우 PR 생성까지 지원할 수 있다.

Agent는 Merge를 수행하지 않는다.

최종 Merge는 프로젝트 소유자가 담당한다.

---

## 작업 흐름

```text
GitHub Issue 생성

↓

Branch 생성

↓

작업 수행

↓

Pull Request 생성

↓

검토

↓

Squash Merge

↓

Issue 자동 종료
```
